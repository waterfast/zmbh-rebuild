# 重构要求与验收标准

本文件记录用户在本任务中明确提出的要求，优先于旧规划中的建议。重构在 `refactor/` 新项目中进行，原工程作为功能与画面对照。

## 必须保持的内容

1. **严格复刻旧版 UI。** 使用原 Scene、节点、位置、尺寸、锚点、格距、字体、贴图、按钮和交互路径。不得擅自增加“重构版”标题、重画按钮、改变分页/背包布局或以简化面板代替原窗口。
2. **主要重构脚本逻辑。** 可替换节点脚本、信号连接与依赖注入方式；可用的原脚本也可以保留。修改节点组织时，必须证明实际布局、显示层级、点击区域及交互不变。
3. **保留原地图和系统功能。** 地图、商店、背包、任务、角色、技能、装备等按原项目逐项迁移；只复制资源或保留按钮，不算完成系统重构。未接通的功能必须记录为未完成。
4. **脚本统一放在 `Script/`。** 游戏脚本按职责在该目录下组织，Scene 挂载其中的脚本；数据可独立放在 `content/`，图集资源可放在 `presentation/`，美术在 `assets/`。自动化 GDScript 同样归入 `Script/tests` 和 `Script/tools`。第三方 Godot 插件保留其要求的 `addons/` 结构；Python 迁移工具留在 `tools/`。
5. **保持旧功能与操作含义。** 重构目标是替换组织框架，不是重做玩法。普攻、技能释放时刻、动画、命中窗口、商城规则和存档流程需要对照原实现。
6. **模块边界清晰。** 控制器负责输入/AI 意图，Actor 组合状态、运动、战斗和表现；装备/技能定义与实例分开，避免再造巨型全局脚本。
7. **如实记录完成度。** `docs/` 持续记录架构、各系统实现逻辑、原版功能对比、测试与缺口。不得把基础框架或原型称为全部旧功能完成。

## 验收方式

- 以原场景为基准比较节点的布局和资源属性；行为脚本差异应可解释。
- 按原操作路径验证每个按钮和系统；点击只弹“尚未迁移”不能算该功能完成。
- 实际运行并截图核对主菜单、地图、背包、任务、商店和战斗表现。
- 自动化测试验证已实现的规则、时序、数据与生命周期；测试通过不能代替画面和全部功能验收。
- 内存措施仍按合理资源生命周期实施；在功能内容未对齐前，不宣称新旧内存下降比例。

## 当前约束说明

先前动态绘制的主菜单、临时背包/任务布局已按原 Scene 纠正；当前主菜单、档位、地图、HUD、背包、任务和商店均以旧 Scene 为显示基准。现有部分战斗公式、怪物行为、技能和商业系统仍未完成原版等价迁移，详见 `07-原版功能对比与完成度.md`。
