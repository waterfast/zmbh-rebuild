# 原版功能对比与完成度

更新时间：2026-09-21

## 1. 当前结论

**尚未完成原项目的所有功能。** `refactor/` 已有可启动的核心架构、32 个迁移关卡和基础战斗/装备/任务/存档流程，但不能据此称为旧项目的完整替代版本。

这里分别记录“代码框架可用”“内容资源迁移”“接入主流程”和“原版行为验收”。其中任何一个完成，都不自动代表另外三项完成。

## 3. 为什么看到方框不代表动画完成

此前测试场景没有统一挂载 ActorView，Actor 的调试绘制会显示方块；此外普攻和冰龙波投射物也存在调试矩形表现。这是不同层次的问题：

1. 身体动作需要场景挂载 ActorView 并绑定状态。
2. 唐僧普通攻击需要恢复远程弹体行为，不能沿用通用近战攻击代替。
3. 弹体必须使用原视觉资源，动画生成时机、飞行方向和碰撞要一起验收。
4. 只有原角色图集能加载，不能证明完整普通攻击或技能表现已经完成。

本轮已修复前三项中的唐僧普攻和冰龙波：从旧 Scene 提取法术图集、动画轨道和碰撞体，使用新版伤害快照结算；角色动画按原释放时刻生成法术，受击/死亡取消未释放效果。实际图像见仓库 `verification/refactor-ui/tang-sanzang-normal-attack.png` 和 `tang-sanzang-ice-dragon-wave.png`，不是占位框。动画系统整体仍是“基础表现层和这一组原版动作已验证，其他动作与特效继续迁移”。

## 5. 内存状态

已经采取按需加载、装备有界 LRU、技能弱缓存、实例只保存变化数据、场景退出释放和敌人数量上限等措施。回收测试能证明特定场景的节点数量恢复，不等同于整机进程内存已经显著下降。

当前没有完成相同关卡、相同角色/怪物/特效、相同预热和重复进出次数下的新旧内存对照。不得写“内存减少某百分比”“旧版全部内存问题已解决”等结论。

## 6. 后续完成顺序

1. 以已迁移的唐僧普攻/冰龙波为样板，继续核对其他角色动作、死亡表现和技能。
2. 继续迁移旧 UI Scene 节点树，绑定新脚本；保留布局并逐按钮验收。
3. 按角色迁移技能行为、动画、帧事件与伤害，对已有原型逐个替换。
4. 按关卡迁移敌人/Boss、机关、掉落、音频和奖励。
5. 补齐法宝、商店、锻造、合成、分解、装备效果与完整任务。
6. 对齐存档和数值，再完成实际画面与性能基准。

“原版功能迁移完成”的判定应是：旧功能清单都有新入口，关键行为和画面可重复验证，未支持的项目有明确处置，且完整游戏流程通过实际运行。当前尚未达到这一条件。
