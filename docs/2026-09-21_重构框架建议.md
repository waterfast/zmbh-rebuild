## 先从 `BaseHero` 开刀

现在的 `BaseHero.gd` 是整个项目最典型的问题。

你可以直接看：

BaseHero.gd

它现在同时干了移动、跳跃、死亡、受伤、技能输入、Buff 判断、装备、法宝、动画、无双、阵法、角色特判等等。

比如它有这种逻辑：

```
if self is role1:
    ...
elif self is role3:
    ...
elif self is role4:
    ...
elif self is role5:
    ...
```

这其实就是一个非常好的重构信号：

> BaseHero 已经知道太多具体角色的事情了。

一个真正的 `Player/Character` 基类根本不应该知道什么是 `role1`、`role2`、`role5`。

理想情况应该是：

```
class_name Actor
extends CharacterBody2D

@onready var motor: CharacterMotor = $CharacterMotor
@onready var stats: Stats = $Stats
@onready var abilities: AbilityController = $AbilityController
@onready var buffs: BuffContainer = $BuffContainer
@onready var state_machine: StateMachine = $StateMachine
```

然后唐僧和悟空的区别来自**配置和技能**：

```
Player
 + TangSengDefinition
 + 唐僧 SkillSet

Player
 + WuKongDefinition
 + 悟空 SkillSet
```

而不是：

```
if self is role2:
if self is role3:
if self is role5:
```

## 第一块真正动手写：CharacterMotor

我尤其建议你从它开始，因为这正好接上你前几天学的 Unity `CharacterMotor` 思路。

现在 `BaseObject.gd` 已经隐约有这个意思：

BaseObject.gd

但它把：

```
移动
HP
攻击字典
冰冻
死亡链接
命中
暴击
```

又全部混在了一起。

我们可以先造一个**极其纯粹的 Motor**：

```
class_name CharacterMotor
extends Node

@export var move_speed := 240.0
@export var jump_speed := 540.0
@export var gravity := 980.0

var body: CharacterBody2D

func setup(actor: CharacterBody2D):
    body = actor

func move(direction: float, delta: float):
    body.velocity.x = direction * move_speed

    if not body.is_on_floor():
        body.velocity.y += gravity * delta

    body.move_and_slide()

func jump():
    if body.is_on_floor():
        body.velocity.y = -jump_speed
```

这样：

```
Player
Enemy
NPC
甚至召唤物
```

都可以复用这套运动组件。

而且 Motor **不知道**：

```
唐僧是谁
悟空是谁
什么是火魔斩
什么是装备
什么是背包
```

这才是一个底层模块应该有的状态。

# 然后才是状态机

这个游戏特别适合状态机，因为你一直在问的：

```
Idle
Run
Jump
Fall
Attack
Skill
Hurt
Stun
Dead
```

其实这个仓库目前主要是用大量：

```
is_attacking
is_be_attacking
is_using_skills
is_stun
is_jump
is_Immobilize
IsSuperArmor
...
```

去拼状态。

时间一长就会出现：

```
is_attacking = true
is_using_skill = false
is_be_attacking = true
is_jump = true
...
```

然后你会开始怀疑：

> 这个组合到底合法吗？

所以我们可以做：

```
Player
│
├── LocomotionStateMachine
│   ├── Idle
│   ├── Run
│   ├── Jump
│   └── Fall
│
└── ActionStateMachine
    ├── Free
    ├── Attack
    ├── Skill
    ├── Hurt
    ├── Stun
    └── Dead
```

这里我反而**不建议只有一个 FSM**。

因为造梦这种横版动作游戏会出现：

```
空中攻击
移动施法
攻击中位移
技能霸体
受击硬直
技能取消
空中技能
```

所以：

**移动状态和动作状态最好分开。**

例如：

```
Locomotion = Jump
Action     = Attack
```

完全合法。

这比：

```
JumpAttackState
RunAttackState
IdleAttackState
JumpSkillState
RunSkillState
...
```

好太多。

# 战斗层也应该单独拿出来

现在仓库里 `BaseMonster.gd` 甚至直接负责玩家打怪时的伤害公式，包括：

```
命中
暴击
Lucky
防御
魔防
等级压制
吸血
减伤
伤害类型
```

BaseMonster.gd

这意味着：

> **“怪物”这个对象正在决定战斗规则。**

这个职责应该移到：

```
CombatResolver
```

变成：

```
var result = CombatResolver.resolve_hit(
    attacker,
    defender,
    hit_data
)

defender.health.apply_damage(result.damage)
```

其中：

```
HitData
 ├── base_damage
 ├── damage_type
 ├── knockback
 ├── hitstun
 ├── crit_allowed
 └── effects[]
```

以后怪物攻击玩家和玩家攻击怪物走的是**同一条管线**：

```
Attacker
   ↓
Hitbox
   ↓
HitData
   ↓
CombatResolver
   ↓
DamageResult
   ↓
Health
   ↓
CombatEvent
```

这个架构会比当前：

```
BaseHero.get_Monster_last_hurt()

BaseMonster.get_Role_last_hurt()
```

两套互相镜像的伤害系统干净很多。

```
Game

```

而不是：

```
Global.addBullet()
Global.addBuff()
Global.addSound()
Global.addBackpack()
Global.addSkillUI()
Global.addMonsterBlood()
Global....
```

但**别第一步碰它**。

# 数据层反而非常适合 Godot Resource

这也是这个项目第二个特别大的改进点。

现在 `PlayerData.gd` 本质上是一个超级大的 Dictionary；装备又集中在巨大的 `AllEquipment.gd` 里。Godot 的 Custom Resource 天生适合做这种结构化游戏数据：字段有类型、Inspector 能编辑、能继承、能保存成版本控制友好的 `.tres`。[![image](https://www.google.com/s2/favicons?domain=https://docs.godotengine.org&sz=128)Godot Engine documentation](https://docs.godotengine.org/en/latest/tutorials/scripting/resources.html?utm_source=chatgpt.com)

以后可以变成：

```
class_name EquipmentDefinition
extends Resource

@export var id: StringName
@export var display_name: String
@export var equipment_type: EquipmentType

@export var hp: float
@export var attack: float
@export var defense: float

@export var effects: Array[CombatEffect]
```

然后：

```
content/items/
    ruyi_jingu_bang.tres
    xuanwu_armor.tres
    ...
```

技能同样。

怪物同样。

这会让“代码”和“游戏内容”真正分开。Godot 本身就是以可复用 Scene 和 Resource 为核心来组织游戏的。[![image](https://www.google.com/s2/favicons?domain=https://docs.godotengine.org&sz=128)Godot Engine documentation](https://docs.godotengine.org/en/latest/getting_started/introduction/key_concepts_overview.html?utm_source=chatgpt.com)

# 所以我们实际第一阶段只重构这 7 个东西

我建议顺序严格按下面走：

1. **Actor / CharacterMotor**：先让一个测试人物可以走、跳、落地。

2. **Stats + Health**：HP、MP、攻击、防御，不接背包。

3. **双状态机**：Locomotion FSM + Action FSM，实现 Idle / Run / Jump / Fall / Attack / Hurt / Dead。

4. **Hitbox / Hurtbox + CombatResolver**：实现“玩家普通攻击 → 怪物掉血 → 受击 → 死亡”。

5. **AbilityController**：只移植一个技能，比如唐僧冰龙波。

6. **BuffContainer**：只移植两个 Buff，比如中毒 + 霸体。

7. **Enemy + EnemyAI**：只移植一只最普通的小怪。

**做到这里以后暂停。**

因为此时我们已经得到一个最小的：

```
玩家
  ↓
移动
  ↓
普攻
  ↓
技能
  ↓
命中
  ↓
伤害
  ↓
Buff
  ↓
怪物 AI
  ↓
死亡
```

完整战斗闭环。

然后我们再把原项目的：

```
Role2
Monster1
```

完整迁过来。

**只要这一对迁成功，后面的 100 多只怪物基本就是内容迁移，而不是重新设计架构。**

### 我会把 Effect 作为整个战斗系统的核心抽象

这是你这个游戏以后最值钱的一层。

比如：

```
class_name Effect
extends Resource

func apply(context: EffectContext) -> void:
    pass
```

具体效果：

```
DamageEffect
HealEffect
AddBuffEffect
RemoveBuffEffect
StatModifierEffect
SpawnProjectileEffect
KnockbackEffect
GrantAbilityEffect
CooldownModifierEffect
```

于是完全不同的东西可以复用同一个 Effect。

例如技能：

```
火魔斩
└── SpawnProjectileEffect
      └── projectile hit:
            DamageEffect
            AddBuffEffect(Burn)
```

装备：

```
烈焰戒指
└── OnHitEffect
      └── AddBuffEffect(Burn)
```

Buff：

```
Burn
└── PeriodicEffect
      └── DamageEffect
```

法宝：

```
紫金铃
└── Ability
      ├── DamageEffect
      └── AddBuffEffect(Stun)
```

底层甚至不知道：

> 这个 DamageEffect 究竟是技能造成的、装备造成的、Buff 造成的还是法宝造成的。

这就是解耦。

---

而且我建议你不要把所有东西都叫 `Effect` 然后最终又变成一个巨型类。

可以分成四层概念：

```
Modifier
    数值修正
    Attack +20%
    Crit +5
    MoveSpeed -30%

Effect
    做一件事情
    Damage
    Heal
    ApplyBuff
    SpawnProjectile

Trigger
    什么时候做
    OnHit
    OnDamaged
    OnKill
    OnSkillUsed
    OnDodge

Ability
    玩家主动发动的一组行为
```

它们组合起来会非常强。

例如一件装备：

```
嗜血魔刃

Modifier:
    Attack +100

Trigger:
    OnDamageDealt

Condition:
    damage_type == PHYSICAL

Effect:
    Heal(damage * 0.10)
```

完全不需要：

```
class BloodSword
```

甚至都不一定需要写新代码。

```
frost_explosion   ← 装备给的
purple_bell       ← 法宝给的
demon_attack      ← Buff 给的
```

而且这里有一个很重要的设计：

**Ability 必须记录 Source。**

比如：

```
AbilityInstance
├── definition = FrostExplosion
└── source = Equipment("冰霜法杖")
```

卸下装备以后：

```
ability_container.remove_by_source(staff)
```

技能自动消失。

否则以后你会遇到这种很恶心的问题：

> 两件装备都提供同一个技能，我卸掉其中一个，技能到底删不删？

所以最好从一开始就：

```
Ability
+
Source
```

而不是只保存技能 ID。

---

Effect 也一样。

比如：

```
Attack +10%
```

可能来自：

```
装备 A
装备 B
Buff C
角色被动
阵法
```

Stats 不应该保存：

```
attack *= 1.1
attack *= 1.2
```

这样最后根本算不回来。

应该：

```
Stats
    base_attack = 100

Modifiers:
    EquipmentA: +20
    EquipmentB: +10%
    BuffC:      +30%
```

计算的时候：

```
final_attack
=
(base + flat_modifier)
* percentage_modifier
```

装备脱掉：

```
remove_modifiers_from_source(equipment_a)
```

这样非常干净。

## 事件系统会成为关键胶水

这里又和你之前 `seer-asio` 的 Effect/Event 思路接上了。

Combatant 可以有：

发出：

```
AfterDamage

OnCrit
OnDamaged
OnKill

OnAbilityHit

OnBuffAdded
OnBuffRemoved
```

装备特殊效果只监听事件。

例如：

```

```

配置：

```

    OnHit

Condition:
    random < 0.2

Effect:
    DamageEffect(
```

角色完全不用知道这个戒指存在。

它只是：

```

    ↓

```

这就是我们要的方向。
